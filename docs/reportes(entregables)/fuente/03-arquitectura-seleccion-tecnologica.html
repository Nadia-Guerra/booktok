DuoBook: la arquitectura que conecta libros, películas y lectores

Preámbulo

DuoBook es una aplicación móvil para registrar, reseñar y comparar libros y sus adaptaciones al cine, y para descubrir obras por las conexiones entre autores, directores, actores y lectores. Sus datos viven en tres bases distintas, y eso plantea una pregunta práctica: ¿cómo habla una aplicación de teléfono con tres bases sin volverse un enredo?

Este documento responde con la arquitectura, es decir, las piezas del sistema, lo que hace cada una y cómo se comunican. Presenta el diagrama general, el reparto de responsabilidades, las tecnologías elegidas y por qué se eligieron frente a otras, y la forma en que se coordinan las operaciones que tocan más de una base.

Se llama obra a un libro o a una película. Los códigos RF y RNF identifican requerimientos funcionales y no funcionales; RN, reglas de negocio, y D, decisiones de diseño registradas en el repositorio.

La arquitectura de un vistazo

DuoBook tiene tres niveles. La aplicación en el teléfono muestra pantallas y envía peticiones. La API (el programa intermedio que recibe esas peticiones) aplica las reglas y es la única que conoce las bases. Las bases de datos guardan la información. Entre el teléfono y la API hay un túnel HTTPS, un canal cifrado que permite llegar desde el teléfono al equipo donde corre el sistema (D-30, D-62).

CaminoQué viaja
App → APIPeticiones HTTPS con el código de sesión. La dirección de la API se puede escribir en la propia app, porque la del túnel cambia en cada arranque
App → sitios externosSolo descarga portadas y fotos; las bases guardan la dirección, no el archivo (D-25, D-31)
Rutas → serviciosDatos con formato ya comprobado y la identidad de quien pide
Servicios → repositoriosLecturas y escrituras sobre una base concreta
Servicios ↔ sincronizadorUn aviso cuando hay un cambio por copiar, y la aplicación de ese cambio

Es un monolito modular (D-29): un solo programa, ordenado por dentro en módulos. Se descartaron los microservicios (un programa por base) y las colas externas de mensajes: para este tamaño añadirían piezas que montar y vigilar sin resolver nada nuevo.

Responsabilidades de cada pieza

Una regla ordena toda la API: cada petición pasa por tres capas y ninguna se salta. Las rutas reciben, los servicios deciden y los repositorios consultan.

La aplicación (frontend)

Sí haceNo hace

Guardar la sesión en el almacenamiento seguro del teléfonoDecidir permisos: ocultar un botón es comodidad; quien protege es la API (RNF-07)

Por dentro se divide en configuración y sesión (core), llamadas a la API (api), lógica reutilizable (hooks), piezas visuales (componentes), pantallas (vistas) y navegación. Un único módulo habla con la API: pone la dirección y la sesión, fija un tiempo límite de 45 segundos y traduce los errores. El límite es holgado porque la primera consulta al grafo después de reiniciarlo puede tardar bastante.

Rutas

Son la puerta de entrada de la API, bajo el prefijo /api/v1. Identifican la sesión y el rol, comprueban el formato de lo que llega (tipos, rangos, largos, identificadores, direcciones https://) y llaman a un servicio. No tienen reglas de negocio ni consultas.

Repositorios

Son el único código que sabe consultar una base: hay un grupo para la relacional, otro para la documental y otro para el grafo. No contienen reglas ni se llaman entre sí. Las consultas del grafo se leen de los mismos archivos que usan las pruebas de la base, así que existe una sola copia de cada una. No se usan ORM ni ODM (capas que generan las consultas solas): se escriben a mano, siempre con parámetros, es decir, sin pegar texto del usuario dentro de la consulta.

Los errores se responden de una sola forma, desde un único manejador que nunca muestra detalles internos de un motor: 400 si la entrada es inválida, 401 sin sesión, 403 sin permiso, 404 si no existe, 409 ante un conflicto o duplicado y 503 si una base no está disponible, que indica que se puede reintentar.

Cómo la aplicación llega a las tres bases

La forma más clara de ver la arquitectura es seguir algunas peticiones de principio a fin.

Abrir la ficha de una película

La ruta recibe el identificador. El servicio de Catálogo pide la ficha a MongoDB (título, sinopsis, plataformas y reparto ya copiado), el promedio a PostgreSQL y los directores y el libro de origen a Neo4j, y completa el título de ese libro con su ficha. La aplicación recibe una sola respuesta: no sabe que intervinieron tres bases.

Publicar una reseña

La ruta comprueba la sesión y el formato. El servicio confirma en MongoDB que la obra esté publicada y pide al repositorio relacional una única transacción (un grupo de cambios que se aplican todos o ninguno): guardar la reseña, actualizar el promedio, marcar la obra como terminada y anotar el evento obra_leida. La API responde en cuanto se confirma. Después, el sincronizador crea en el grafo la relación leyó, solo si la obra es un libro.

Recomendar libros

Es una operación que cruza dos bases en dos pasos. PostgreSQL entrega los libros que «gustaron» a la persona (terminados y calificados con 4 o más). Neo4j parte de ellos y salta a otros libros adaptados por el mismo director. MongoDB pone los títulos y las portadas.

Dar de alta una película

El servicio de Administración comprueba que el alta trae libro de origen, director y reparto. Luego crea la ficha como borrador, registra la obra en PostgreSQL, crea el nodo y sus relaciones en Neo4j, copia el reparto a la ficha, verifica el mínimo y por último la publica. Si un paso falla después de crear la ficha, la API responde con el identificador para completar la publicación sin repetir el alta (D-58).

REST frente a GraphQL

Se comparó también el estilo de la API. GraphQL permite que el cliente arme sus propias consultas, pero aquí hay un solo cliente y un conjunto de operaciones conocido; habría añadido librerías en ambos lados, riesgo de encadenar consultas a tres bases y otra forma de manejar errores. Se eligió REST, documentada con OpenAPI, un archivo que describe cada operación (D-52). Hoy describe 41.

MongoDB aporta lo que el diseño documental usa: datos anidados, validación de estructura, índices únicos y búsqueda de texto. No se compararon otros motores documentales. Neo4j aporta recorridos de longitud variable y búsqueda de caminos; tampoco se compararon otros, y se usa la edición Community por ser gratuita, aceptando que los campos obligatorios y los tipos los garantice la API.

La pregunta más fuerte fue si hacían falta tres bases. «Todo en PostgreSQL» funcionaría en un sistema pequeño, pero buscar un camino de longitud desconocida entre autores, libros, películas y actores obligaría a imitar un grafo con tablas. «Todo en MongoDB» dejaría en manos de la aplicación el borrado en cadena sin dejar registros huérfanos.

Ejecución local y túnel

Las tres bases y la API corren con Docker Compose en el equipo de desarrollo, y el teléfono llega por un túnel HTTPS, que además es necesario porque Android bloquea por defecto las conexiones sin cifrar (D-30). Se descartaron una máquina virtual pública, que pedía pago o tarjeta y más configuración, y los servicios gratuitos que se duermen por inactividad: con la API dormida, el sincronizador dejaría de trabajar. Para el túnel se eligió Cloudflare sobre ngrok porque no exige crear una cuenta (D-62).

Memoria: un límite por contenedor

Con poca memoria y otros proyectos en el mismo equipo, cada contenedor tiene un tope y su programa se ajusta para respetarlo (D-36). Los servicios se levantan por perfiles, de modo que solo arranca lo que se necesita.

ServicioTopeAjuste interno

Cada base declara una comprobación de salud para que la API pueda esperar a que estén listas. Las bases y la API solo escuchan en el propio equipo, y las contraseñas de las bases se leen de un archivo de configuración que no se guarda en el repositorio; el repositorio incluye un ejemplo sin valores reales.

Sesión y contraseñas

Al iniciar sesión, la API genera un token (un código aleatorio) y guarda en la base solo su huella; vence a los 30 días. Se descartó el JWT, un token firmado que no se consulta en la base: de todos modos habría que consultarla para saber si la cuenta sigue existiendo, y cerrar sesión no lo invalidaría (D-35). Las contraseñas se guardan con bcrypt, un método deliberadamente lento que dificulta adivinarlas. Si el correo no existe o la contraseña falla, la respuesta es la misma.

Fuente de verdad y sincronización

Con tres bases, cada dato necesita un dueño. La fuente de verdad es la base donde un dato se modifica oficialmente; las copias existen para no encadenar consultas y nunca se editan a mano.

La bandeja de salida

No existe una transacción que abarque tres bases. Para las copias que salen de PostgreSQL se usa una bandeja de salida: la misma transacción que guarda el dato anota un evento en la tabla sync_outbox. Así no puede existir el dato sin su aviso pendiente. Los eventos son usuario_creado, usuario_eliminado, seguimiento_creado, seguimiento_eliminado, obra_leida y obra_no_leida.

El sincronizador

Un proceso dentro de la API, el sincronizador o worker, aplica esos eventos. Su comportamiento está pensado para que un fallo no desordene ni pierda nada:

  • Procesa de uno en uno, en el orden en que nacieron, en lotes de 50.
  • Se despierta con un aviso interno justo después de confirmarse la transacción y, como respaldo, revisa cada 30 segundos. Al arrancar vacía primero lo pendiente.
  • Cada operación es idempotente: repetirla no duplica nada.
  • Si una base no responde, hace pausas cada vez más largas (2, 4, 8 segundos, hasta 30) sin contar intentos.
  • Si el que falla es el evento, suma un intento; al quinto lo marca fallido y continúa con los demás. Mientras tanto no salta al siguiente, para no invertir el orden.
  • Al apagar la API termina el evento en curso y no toma otro.

Para enterarse de los cambios se compararon varias formas (D-34). Preguntar a la base cada 2 segundos suponía unas 43 200 consultas diarias en reposo. El aviso interno con revisión cada 30 segundos las reduce a unas 2900 y reacciona en milisegundos. Las herramientas externas de colas se descartaron por memoria y complejidad. Este diseño tiene una condición: solo puede correr una copia de la API, porque dos sincronizadores romperían el orden.

Las otras dos direcciones

El alta de una obra no usa la bandeja: es una secuencia ordenada que termina al publicar la ficha, y cada paso puede repetirse sin daño. El reparto viaja del grafo a la ficha: la API lo lee completo en Neo4j y reemplaza la lista de la película. Registrar una adaptación bloquea antes el nodo de la película, para que dos escrituras simultáneas no le den dos libros de origen (D-23).

Cuando algo falla a medias

SituaciónQué ocurre
Falla la transacción de una reseñaNo cambia nada
La reseña se guarda y el grafo está caídoReseña y promedio quedan correctos; la lectura llega al grafo cuando vuelva
Se interrumpe un altaLa obra queda en borrador y no se muestra; se puede completar
Se elimina una cuenta y falta limpiar copiasLa cuenta ya no existe; el evento se reintenta
El grafo no responde al crear una comparativaNo se guarda y se responde un error recuperable

Hay una consecuencia que se aceptó desde el principio: la consistencia eventual. Entre que se guarda un dato y llega a su copia pasa un instante en el que, por ejemplo, una recomendación todavía no cuenta una lectura recién registrada.

La reconciliación

Como red de seguridad existe un comando que se lanza a mano y compara copias con su fuente. En su versión actual revisa los seguimientos y los libros leídos, informa los eventos pendientes o fallidos y, solo si se le pide, corrige el grafo (D-64). No corrige mientras haya eventos pendientes.

Cómo se comprobó que la arquitectura se respeta

Las reglas de capas son fáciles de escribir y fáciles de romper con prisa, así que se revisaron sobre el código: ningún archivo de rutas importa un repositorio, ningún servicio contiene consultas y ningún repositorio usa a otro. El orden de los eventos con operaciones simultáneas sobre un mismo seguimiento y un mismo estado tiene su propia prueba automática (backend/test/orden-eventos.test.ts), igual que la reconciliación.

Limitaciones

  • Solo puede ejecutarse una copia de la API, así que no escala agregando copias.
  • Mientras la API se reinicia, la propagación se detiene; los eventos esperan en la bandeja.
  • La ejecución depende del equipo local y de su conexión; con el túnel abierto, la API es accesible desde internet para quien conozca la dirección.
  • La reconciliación es reducida: no repara fichas, reparto, promedios, registros huérfanos ni borradores.
  • No se purgan los eventos ya procesados ni las sesiones vencidas, aunque el diseño lo prevé.
  • bcrypt solo considera los primeros 72 bytes de una contraseña (D-61).
  • Las imágenes dependen de sitios externos, que pueden cambiarlas o retirarlas.
  • Express no impone las capas: se mantienen por disciplina.

Conclusión

La arquitectura de DuoBook se resume en una idea: la aplicación pide, la API decide y cada base guarda lo que mejor sabe guardar. Las capas evitan que las reglas se mezclen con las consultas; la fuente de verdad dice quién manda sobre cada dato, y la bandeja de salida lleva los cambios a sus copias sin perderlos. Así, una pantalla que parece sencilla puede reunir libros, películas y lectores desde tres bases distintas.
