DuoBook: comprobar que funciona y que otra persona pueda levantarlo

Preámbulo

DuoBook es una aplicación móvil para registrar, reseñar y comparar libros y sus adaptaciones al cine, y para descubrir obras por las conexiones entre autores, directores, actores y lectores. Construirla fue la mitad del trabajo. La otra mitad es responder dos preguntas: ¿cómo se sabe que funciona? y ¿podría otra persona ponerla en marcha?

Este documento cuenta qué se probó y con qué resultado, cómo se midió el rendimiento, cómo se instala y ejecuta el proyecto y qué queda pendiente. Solo se presenta como hecho lo que se ejecutó. Se llama obra a un libro o a una película; RF y RNF son requerimientos funcionales y no funcionales, y D, una decisión de diseño.

Qué significa probar aquí

Cada prueba responde tres cosas: qué se hace, qué debe pasar y qué evidencia queda. Por ejemplo, se publica una reseña de 5 estrellas; el promedio de la obra debe recalcularse y la obra quedar como terminada; y la salida de la prueba automática se guarda en un archivo.

Las pruebas se organizaron en etapas y se ejecutaron el 26 de noviembre en un equipo con Windows 11, 6 GB de memoria (Docker ve unos 3 GB), Node 24.14.0, PostgreSQL 18.7, MongoDB 9.0.4 y Neo4j 5.26.34 Community. Los casos en el teléfono se recorrieron el 27 de noviembre.

A mitad del trabajo se ampliaron los datos de ejemplo, la semilla: pasó de 11 libros y 12 películas a 17 y 18. Por eso este documento indica en cada resultado con qué datos se obtuvo.

El escenario de reconciliación

El curso pide demostrar que una copia desactualizada no pasa inadvertida. Con dos lectores de prueba, se borraron sus relaciones solo en el grafo.

Pruebas funcionales en el teléfono

La API y las tres bases corrían en el equipo y el teléfono llegaba a ellas por un túnel seguro y temporal. Se usaron la semilla ampliada, una cuenta de prueba nueva y la cuenta de administrador de ejemplo. Alta de un libro y su película

Además de los casos previstos, desde el teléfono se registraron como administrador las personas, un libro y su película. Es la operación que más bases cruza. Se comprobó por HTTP que ambas obras quedaron publicadas y aparecen en la búsqueda pública.

Otras pantallas

Lo que no salió como se esperaba

En el teléfono no cargaron los pósteres de las películas ni las fotos de las personas; las portadas de los libros sí. En su lugar se ve el reemplazo previsto, con el título o las iniciales, y la aplicación sigue funcionando. Esas direcciones son de Wikimedia, que además de pedir que la aplicación se identifique limita las peticiones seguidas: al pedir desde el equipo varias imágenes a la vez, respondió «demasiadas peticiones» (código 429) a la mayoría. Después de las capturas se añadió que la aplicación reintente cada vez más tarde; en una simulación desde el equipo cargaron las 65 imágenes de Wikimedia, la última a los 89 segundos. Falta comprobarlo en el teléfono.

Las pantallas todavía muestran el nombre de trabajo del proyecto, «Del Libro a la Pantalla», en lugar de DuoBook.

Rendimiento

Condiciones de la medición

Un script llama a la API por HTTP, hace 5 llamadas de calentamiento y mide 50 por flujo, una a la vez y desde el mismo equipo (AMD Ryzen 5 3550H, 5,9 GB de memoria, 0,5 a 0,7 GB libres). Datos: la semilla ampliada, con 93 nodos en el grafo. Se corrió dos veces. La mediana es el tiempo que la mitad no supera; el percentil 95 (p95), el que no superan 95 de cada 100. La meta fue un p95 de 1 segundo, y de 2 para los recorridos del grafo.

Todos los flujos cumplieron su meta. Iniciar sesión es el más lento a propósito: comprobar la contraseña cuesta tiempo para dificultar adivinarla.

La primera consulta después de reiniciar

Se reinició Neo4j dos veces y se midió la primera llamada. Las recomendaciones de libros tardaron 11,5 y 4,2 segundos, y los caminos 3,5 y 1,2; la segunda llamada bajó a milisegundos. Esa primera consulta puede incumplir la meta de 2 segundos. Antes de una demostración conviene abrir una vez las recomendaciones y los caminos.

Qué no dicen estas cifras

Se midieron con una sola persona usando el sistema y un catálogo pequeño: no predicen cómo respondería con muchas personas a la vez ni con miles de obras.

Instalación y ejecución

El código está en https://github.com/Nadia-Guerra/booktok. Las instrucciones completas están en el README.md de la raíz.

Requisitos

QuéPara qué
Windows 10 u 11 con PowerShell 5.1Los scripts de las bases
GitDescargar el proyecto
Node 24API, aplicación y pruebas
Docker Desktop abiertoLas tres bases y la API
cloudflaredLlegar a la API desde un teléfono
Expo Go en un teléfono AndroidAbrir la aplicación en desarrollo

Instalar, configurar y cargar

git clone https://github.com/Nadia-Guerra/booktok.git
cd booktok
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
Copy-Item .env.example .env
npm ci
.\db\scripts\reconstruir.ps1 -SinPruebas
docker compose --profile api up -d --wait --build
curl.exe http://127.0.0.1:3000/api/v1/salud

La tercera línea solo hace falta si Windows bloquea los scripts. En la cuarta se crea la configuración, cuyas claves se cambian. La sexta crea las tres bases y carga los datos de ejemplo; pide confirmación porque borra lo que hubiera en las bases del proyecto. La última debe responder que las tres bases están bien.

Ejecutar cada día

Las bases se levantan de una en una y después la API, para no agotar la memoria:

docker compose --profile postgres up -d --wait
docker compose --profile mongo up -d --wait
docker compose --profile neo4j up -d --wait
docker compose --profile api up -d --wait

Solo debe haber una copia de la API, porque lleva dentro el sincronizador.

Abrir la aplicación en desarrollo

cloudflared tunnel --url http://localhost:3000
npm run app

El primer comando crea un túnel, una dirección segura y temporal; mientras esté abierto, la API es accesible desde internet. El segundo, en otra terminal, muestra un código QR para abrir la aplicación con Expo Go. En la aplicación, en la pantalla de conexión, se pega la dirección del túnel.

Repetir las pruebas

npm run typecheck
npm test --workspace frontend
npm run test:unitarias --workspace backend
docker compose stop api
npm test
docker compose --profile api up -d --wait
.\db\scripts\coherencia.ps1
node test/rendimiento/medir.mjs

Para la suite completa se detiene la API, porque su sincronizador se llevaría los cambios que las pruebas necesitan observar.

El ejercicio fue útil porque encontró fallas en la documentación: el README no explicaba cómo descargar el proyecto ni avisaba del permiso para ejecutar scripts, y se reescribió. También mostró que instalar con la opción --prefer-offline falla si la caché local es antigua; con npm ci normal, que es lo que indica la guía, funciona. No se probó en otra computadora.

Pendientes

Estos puntos aún no se han realizado:

  • Compilar el APK, el archivo instalable de la aplicación para Android.
  • Pruebas funcionales con el APK instalado, incluidos los casos que quedaron parciales o sin evidencia.
  • Comprobar en el teléfono la corrección de las imágenes que no cargaban.
  • Despliegue y demostración con la aplicación instalada.

Limitaciones

  • Las pruebas de cada base, la reconstrucción desde cero y la instalación limpia son anteriores a la ampliación de la semilla.
  • La instalación no se ha probado en otra computadora ni en otro sistema operativo.
  • No hay pruebas automáticas de las pantallas.
  • Los casos en el teléfono se hicieron con Expo Go, en un solo dispositivo, y no todos tienen evidencia completa.
  • No se midió el rendimiento con varias personas a la vez ni con un catálogo grande.
  • La suite completa tarda según la memoria libre y conviene ejecutarla sin otros programas pesados.

Conclusión

Lo que se probó del servidor y de las bases responde como se diseñó: 119 pruebas automáticas correctas, las tres bases coherentes y los flujos principales muy por debajo de su meta de tiempo, con una excepción conocida en la primera consulta al grafo. La instalación está documentada y se ensayó desde una copia limpia. En un teléfono real, con Expo Go, los flujos principales funcionaron, con las imágenes de películas y personas como falla conocida. Falta comprobar su corrección, llevar la aplicación al teléfono como APK, probarla ahí y desplegarla.
