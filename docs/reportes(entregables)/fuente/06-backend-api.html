DuoBook: el intermediario que coordina las tres bases

Preámbulo

DuoBook es una aplicación móvil para registrar, reseñar y comparar libros y sus adaptaciones al cine, y para descubrir obras por las conexiones entre autores, directores, actores y lectores. Entre las pantallas y las tres bases de datos hay una pieza que no se ve y sin la cual nada funcionaría: el backend, el programa que recibe las peticiones, aplica las reglas y decide qué base consultar.

Su puerta de entrada es la API, el conjunto de operaciones que la aplicación puede pedirle. Este documento cuenta qué estilo de API se eligió, cómo está organizado el código, cómo se conecta con las bases, cómo valida, autoriza y responde a los errores, dónde guarda sus credenciales y cómo se documenta y se prueba.

Se llama obra a un libro o a una película. RF identifica un requerimiento funcional; RN, una regla de negocio, y D, una decisión de diseño.

La decisión: una API REST

Una API REST organiza sus operaciones como direcciones web: se pide una ficha con GET /obras/{id}, se publica una reseña con PUT y se elimina con DELETE. Los datos viajan en JSON, un formato de texto con nombres y valores. Todas las direcciones empiezan por /api/v1, de modo que una versión futura no rompa las aplicaciones instaladas.

La alternativa era GraphQL, donde el cliente compone sus propias consultas. Se descartó (D-52): hay un solo cliente y un conjunto de operaciones conocido; habría añadido librerías en ambos lados, el riesgo de encadenar consultas a tres bases sin control y una forma distinta de manejar errores. La autorización, además, se aplica con naturalidad operación por operación.

Está escrita en TypeScript sobre Node 24 con Express 5 (D-32, D-60). Es un solo programa, ordenado en módulos, que lleva dentro el sincronizador que copia cambios entre bases (D-29).

Cómo está organizado

El código se divide en tres carpetas: backend/ (la API), frontend/ (la app) y shared/, con las definiciones de datos que usan las dos (D-53). Dentro del backend, tres capas separan responsabilidades.

CapaQué haceQué tiene prohibido
Rutas (controladores)Reciben la petición, comprueban sesión, rol y formato, y llaman a un servicioReglas de negocio y consultas
ServiciosAplican las reglas, ordenan los pasos y combinan basesEscribir consultas
RepositoriosEjecutan las consultas de una sola baseReglas y llamarse entre sí

Hay nueve archivos de rutas, un servicio por área (cuentas, catálogo, reseñas, listas, social, comparativas, descubrimiento, administración, sincronización y reconciliación) y tres carpetas de repositorios: relacional, documental y grafo. En el código, cada consulta anota el identificador del catálogo de operaciones (por ejemplo O7 o AP-18), para poder rastrearla.

La ruta de publicar una reseña muestra lo delgada que es la primera capa: valida los datos, llama al servicio y elige el código de respuesta.

rutasResenas.put('/obras/:obra_id/resena', exigirSesion, async (req, res) => {
  const { obra_id } = parametrosObra.parse(req.params);
  const entrada = resenaEntrada.parse(req.body ?? {});
  const { creada, ...cuerpo } = await resenas.publicar(sesionDe(res), obra_id, entrada);
  res.status(creada ? 201 : 200).json(cuerpo);
});

Conexión con las bases

Cada motor se usa con su controlador oficial, la librería que el propio fabricante o su comunidad mantienen: pg para PostgreSQL, mongodb para MongoDB y neo4j-driver para Neo4j. No se usan capas que generen consultas automáticamente (ORM u ODM): así se ve exactamente qué se ejecuta. La conexión con cada base vive en un módulo propio.

Validación de entradas

Todo lo que llega se revisa antes de tocar una base, con Zod, una librería que describe cómo debe ser cada dato. Las definiciones están en shared/ y las usa también la aplicación, de modo que el formulario avisa pronto y la API vuelve a comprobar: nunca se confía en el teléfono (D-37).

export const resenaEntrada = z.object({
  calificacion: z.number('La calificación es un número del 1 al 5')
    .int('La calificación es un número entero')
    .min(1, 'La calificación mínima es 1')
    .max(5, 'La calificación máxima es 5'),
  texto: z.string() ...   // hasta 3000 caracteres
});

Entre otras cosas se exige: identificadores y correos en minúsculas, contraseñas de al menos 8 caracteres, calificaciones de 1 a 5, imágenes con https://, repartos sin personas ni posiciones repetidas y un máximo de 100 KB por petición. Los listados largos se entregan en páginas de 20 (hasta 50) con un cursor, una marca de por dónde seguir; el cursor se valida y conserva la hora con precisión de millonésimas de segundo para no saltarse filas.

Autorización: quién puede qué

Al iniciar sesión, la API entrega un token, un código aleatorio que la aplicación presenta en cada petición. En la base solo se guarda su huella, así que aun leyendo la base no se podría usar. Vence a los 30 días y cerrar sesión lo elimina (D-35). El rol se consulta en cada petición, por lo que un cambio surte efecto de inmediato.

export const exigirAdmin: RequestHandler = async (req, res, next) => {
  const sesion = await sesionDeLaCabecera(req);          // 401 sin sesión
  if (sesion.rol !== 'admin')
    throw new ErrorApi('sin_permiso', 'Solo el administrador puede hacer esto');
  res.locals.sesion = sesion;
  next();
};

Además del rol, está la propiedad (RN-10): al editar o borrar, la consulta incluye el identificador de quien tiene la sesión, así que nadie toca lo ajeno. El administrador sí puede moderar. Las contraseñas se guardan con bcrypt, deliberadamente lento (D-61). Si el correo no existe o la contraseña falla, la respuesta es idéntica y tarda parecido: se compara contra una huella señuelo, para no revelar qué correos están registrados.

Manejo de errores

Un solo manejador convierte cualquier fallo en una respuesta con la misma forma: un código, un mensaje en español y, si aplica, qué campo está mal. Nunca incluye trazas ni mensajes crudos de un motor.

La API distingue un fallo de la petición de un fallo de la base: reconoce errores de red, bases que están arrancando y esperas agotadas, y los responde como 503. Los registros anotan método, ruta, estado y duración; nunca cuerpos, cabeceras ni parámetros de búsqueda.

Consultas parametrizadas

Una consulta parametrizada envía por separado la instrucción y los datos, de modo que un texto escrito por alguien nunca se interpreta como parte de la orden. Así se evita la inyección. Las tres bases lo hacen:

// PostgreSQL: los valores van en $1, $2
cliente.query('SELECT resena_id FROM resena
               WHERE usuario_id = $1 AND obra_id = $2 FOR UPDATE', [usuario, obra]);

// MongoDB: filtros construidos solo con datos ya validados
{ $match: { $text: { $search: texto }, estado_publicacion: 'publicada' } }

// Neo4j: parámetros con nombre
leerGrafo(CG01, { texto: consulta });

Hay dos cuidados propios. En MongoDB, validar primero los tipos impide que alguien envíe un operador como $ne en lugar de un texto. En Neo4j, la búsqueda por nombre interpreta ciertos símbolos como órdenes, así que se eliminan antes de enviarla, y si no queda nada no se consulta (D-41).

Configuración y credenciales

La API lee su configuración de variables de entorno, valores que se le pasan desde fuera del código: puertos, nombres de las bases, usuarios y contraseñas. Se toman de un archivo .env que no se guarda en el repositorio, y hay un .env.example con la lista. Al arrancar se comprueba que estén todas; si falta alguna, el programa se detiene y nombra la variable, nunca su valor.

La API como coordinadora

El valor del backend está en las operaciones que cruzan bases y en las reglas que ninguna base puede imponer sola.

Publicar una reseña

El servicio comprueba que la obra esté publicada, pide a PostgreSQL una sola transacción (reseña, estado «terminada» y evento) y avisa al sincronizador. El promedio lo calcula la base. Si la persona ya tenía una reseña de esa obra, la misma operación la edita.

Comparar un libro con su película

Antes de guardar, el servicio pide las dos fichas a MongoDB y pregunta al grafo si la película es adaptación del libro (RN-06). Si no lo es, responde 409; si el grafo no responde, no guarda nada.

Recomendar

PostgreSQL entrega los libros que gustaron; Neo4j busca otros por el mismo director y los de las personas seguidas; MongoDB completa títulos y portadas.

Dar de alta una obra

No hay una transacción que abarque tres bases, así que el servicio sigue un orden: ficha como borrador, registro en PostgreSQL, nodo y relaciones, copia del reparto, comprobación del mínimo y publicación. Si falla después de crear la ficha, responde 503 con el identificador para completar la publicación sin duplicar (D-58). La respuesta nunca dice que todo salió bien si no fue así.

Copiar los cambios

El sincronizador toma los eventos pendientes en orden, los aplica de forma repetible, espera si una base está caída y aparta como fallido el que falla cinco veces por sí mismo. Un comando de reconciliación revisa seguimientos y libros leídos contra el grafo (D-64).

Documentación del contrato

El contrato está en docs/api/openapi.yaml, en formato OpenAPI: un archivo estándar que describe cada operación, lo que recibe, lo que responde y sus errores, y que herramientas habituales pueden leer. Describe las 41 operaciones construidas. El documento docs/api/endpoints.md conserva la propuesta completa de 51. La interfaz no contiene credenciales ni conexiones a bases: solo conoce este contrato.

Limitaciones

  • De las 51 operaciones propuestas, diez no se construyeron: consultar una comparativa suelta, cambiar la foto de una persona, corregir una obra, corregir o quitar ediciones y plataformas, agregar relaciones o el libro de origen a una obra ya creada, y consultar el estado de la sincronización.
  • No hay límite de intentos de inicio de sesión ni de peticiones.
  • Solo puede ejecutarse una copia de la API.
  • La reconciliación es reducida y no se purgan eventos procesados ni sesiones vencidas.
  • La validación del ISBN no comprueba su dígito de control.
  • El contrato OpenAPI se mantiene a mano junto al código.

Conclusión

El backend de DuoBook cumple su papel de intermediario: la aplicación pide en un solo idioma y recibe una sola respuesta, aunque detrás intervengan tres bases distintas. Las reglas viven en un lugar, las consultas en otro y los errores se cuentan de una sola manera.
